# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Desk-HUD is a side-monitor dashboard (1480×320 touch screen) running on a Raspberry Pi. A Node.js server (Express + Socket.IO) and a Pixi.js browser client run on the same device; the client is shown in a kiosk browser at `http://localhost:3000`.

## Commands

```bash
npm i                      # install deps
npm run deploy-local       # start backend via pm2 (watches files, DHUD_ENV=development)
npm run undeploy-local     # stop the local pm2 app
npm run watch              # webpack dev build of the frontend in watch mode
npm run build              # production frontend build
npm run build-demo         # build demo mode (simulated data) into dist/demo
npm run serve-demo         # serve dist/demo
npm run deploy             # pm2 deploy to the Pi (deskhud@10.168.168.159, see ecosystem.config.js)
node ./google_auth.js      # one-off Google OAuth flow; writes tokens into the config file
```

There is no test suite or linter.

Backend logs stream to the browser dev-tools console (`log` socket event), and the server uses livereload, so the page refreshes when the backend restarts.

## Configuration

The backend reads `desk-hud-config.json` from the repo root (gitignored), or the path in the `DHUD_CONFIG` env var. `desk-hud-config.default.json` is the committed template; keep it in sync when adding config keys. `.env` is loaded via dotenv. Parameters are documented in [doc/configuration.md](doc/configuration.md). `Config.getProp('a.b.c')` **throws** if a key is missing or falsy, so any new config key a service reads must exist in the config file.

## Build layout

- Webpack entry: `src/frontend/index.js` → output `src/backend/www/js/app.js`, served statically by Express.
- `build/index.html` (HTML template), `build/assets/` and `build/js/` (vendored Pixi, socket.io client, fonts) are copied into `src/backend/www/` during the build. Edit the files in `build/`, not the copies in `src/backend/www/`.
- `src/backend/www/` (including the compiled `app.js`) is committed. Rebuild after changing frontend code.
- Pixi.js and socket.io are loaded as globals (`PIXI`, `io`) from `<script>` tags, not imported.
- `BUILD_DEMO_MODE` is injected by webpack's DefinePlugin. Demo mode can also be turned on at runtime with the `#demo` URL hash.

## Architecture

Each feature is a **widget** (frontend, ES modules) paired with a **service** (backend, CommonJS), and both live together in `src/widgets/<name>/`. Both sides use the same string id to link them.

- **Registration**: frontend widgets are listed in `src/widgets/widgets.js`; backend services in `src/widgets/services.js`. `DistanceService` and `SysMonitorService` are core services that `src/backend/index.js` adds directly. They emit their own `distance` and `system` events instead of `widget`.
- **Service** (`src/backend/services/Service.js`): constructor is `super(config, io, webApp, id)`. Implement `start()` (usually a `setInterval` polling loop), `welcomeClient(socket)` (send the current state to a new client), and `onMessage(payload)` (handle commands from the client). `this.emit(payload, socket?)` sends `{widgetId, payload}` on the `widget` event. Emitting `{error: "..."}` puts the widget into its error state, and `{error: null}` clears it.
- **Widget** (`src/frontend/Widget.js`, extends `PIXI.Container`): `super(id, title)`. Override `msg2state(msg)` to map a service payload into state (`initState` / `this.state`). Override `onConfig(cfg)` for config that the server pushes in the `config` event (only `dateTime` is sent, chosen in `src/backend/index.js`). Use `sendMessage(payload)` to send commands to the service, and `render(renderer)` for per-frame drawing. Animations are driven by `this.progress`.
- **WidgetContainer** routes socket messages to widgets by id and handles layout, sleep and wake (triggered by distance events), and the system/CPU fan UI.
- **UI building blocks**: `src/frontend/components/` and `src/frontend/circles/`. These are reusable Pixi components that take a `progress` value for appear/disappear animations.
- **Text size**: every `TextField` is drawn at `TEXT_SCALE` (`components/TextField.js`) on top of its `fontSize`. Text that is space-padded to line up with a grid (forecast rows, calendar hour scale) opts out with `scale.set(1)`, and code that measures text with `PIXI.TextMetrics` must multiply by the field's `scale.x` (see `DateScreen`).
- **Weather widget**: `WeatherService` uses the US National Weather Service API (no key; it sends a User-Agent naming the repo, which NWS requires). It looks up the grid point and nearby stations once a day, checks alerts every 2 minutes and the latest observation and hourly/daily forecasts every 10 minutes; each part keeps its last good data if a request fails. NWS icon URLs are mapped to OpenWeatherMap-style codes (`01d`…`50n`) so `weatherIcons.js` glyphs still apply. A new *warning* (severe/extreme) emits `wake` (handled in `WidgetContainer`) and `activate` (only when the widget isn't already in front, because activating the front widget swaps it away), and opens the ALERTS tab.
- **Network widget**: `NetworkService` samples every 30 s with local tools only (`ip route` for the router, `ping` to it and to 1.1.1.1, `dns.lookup` of the hosts the other services use, `/proc/net/wireless` for `wlan0` signal), keeps 24 h of samples in `node-persist` (`network.history`) and downloads 10 MB from Cloudflare's speed endpoint every 3 hours or when the widget's button is tapped.
- **F1 widget**: `F1Service` reads Jolpica-F1 (`api.jolpi.ca/ergast/f1`, the Ergast successor; no key) every hour: driver and constructor standings for `current` (falling back to the previous season before a season's first race) and the race calendar, sent as `weekends` (each session has an `id` like `19:Q` and a code P1/P2/P3/SQ/SP/Q/GP). Session results come from OpenF1 (`api.openf1.org`, free for historical data), whose session list is matched to the calendar by code and start time (±3 h) for each session's OpenF1 `key`. **While any F1 session is live, OpenF1 answers 401 to free users for everything, past sessions included**, so: its session list and every finished session's results are saved in node-persist (`f1.openf1Sessions`, `f1.results`); finished sessions of the last two weekends are prefetched after each hourly refresh (in the gaps between sessions); Q, SP and GP fall back to Jolpica (`<season>/<round>/qualifying|sprint|results.json`, team colours from `TEAM_COLOURS`); and the service retries every 10 minutes while OpenF1 is closed (`openf1` in the payload says why). The RACES tab asks with `{action: 'results', id}`; the answer is a separate `{results: {id, rows | error}}` message (the widget's `msg2state` passes it to `RacesScreen` and returns null). OpenF1 allows 3 requests/s, so its requests are spaced 400 ms apart with retries on 429. Tabs: drivers (two columns of 12), teams, races (swipe through weekends; INFO or a session's results).
- **Sports widget**: `SportsService` reads ESPN's undocumented public API (`site.api.espn.com/apis/site/v2/sports/<sport>/<league>` for teams, team info, schedules and scoreboards; `/apis/v2/sports/.../standings?level=3` for standings, which are unsorted, so the service ranks them) for the teams in `sports.teams` (ESPN abbreviations per league: nfl, mlb, nhl, mls = `soccer/usa.1`, nwsl = `soccer/usa.nwsl`; soccer team pages need ESPN's numeric id, which the service looks up from the team list). One 30 s loop refreshes each league hourly and, when a team's game is due or running, reads that day's scoreboard (US Eastern dates) for the live score; a finished game refreshes the league 5 minutes later. In the off-season the last season's schedule is read with `?season=<year>&seasontype=2`. The widget emits `activate` when a game it hasn't seen live before goes live (games live at page load are only remembered). The main screen has its own league buttons (MainScreen has only three tabs); swipe up/down switches teams within a league.
- **Horoscope widget**: `HoroscopeService` for `horoscope.sign`. TODAY: FreeAstroAPI (`api.freeastroapi.com/api/v2/horoscope/daily/sign`, `x-api-key` header from `horoscope.apiKey` or `FREE_ASTRO_API_KEY`; free plan 80 requests/day, 1/s) with an explicit local `date` (its `today` follows UTC), every 3 h and at local midnight; its lucky time window is UTC and is sent as timestamps. The key must stay server-side: never send it to the client or log it. WEEK and MONTH (and TODAY without a key or when FreeAstroAPI fails): FreeHoroscopeAPI (`freehoroscopeapi.com/api/v1/get-horoscope/{daily|weekly|monthly}?sign=`, no key; its terms require the visible "Powered by FreeHoroscopeAPI" credit, shown by `ReadingScreen`/`DailyScreen`; no date parameter, its day starts before US time; weekly often times out with 504). Weekly every 6 h, monthly every 12 h, failures retried every 15 min; each period keeps its last good reading in node-persist (`horoscope.readings`). Readings are plain `PIXI.Text` (mixed case, sized 14 down to 10 to fit); the circle's zodiac symbol uses DejaVu Sans, which the Pi has (ShareTechMono has no zodiac glyphs).
- **Word of the Day widget**: `WordService` reads Merriam-Webster's public RSS feed (`merriam-webster.com/wotd/feed/rss2`, no key; the dictionary API has no word of the day) hourly. The feed holds the last 10 days; `parseItem` turns each item's HTML description into plain fields (pronunciation, part of speech, definition, example, quote and source, "Did you know?"). Each word's `day` comes from the date as written in `pubDate` (midnight New York time is the evening before in Central time). The list is kept in node-persist (`word.items`). Tabs: word, in use, did you know; swipe right for older words, and it returns to today after 2 minutes. The screen credits Merriam-Webster.
- **Bambu widget** (`src/widgets/bambu/`, title "Printers"): `BambuService` connects to each printer in `bambu.printers` over LAN MQTT (`mqtts://<host>:8883`, user `bblp`, password = the LAN access code, self-signed certificate) with the `mqtt` package, subscribes to `device/<serial>/report` and sends only `pushall` (on connect and every 10 min), never control commands. P1/A1 send partial reports, so each report's `print` object is deep-merged into one state per printer (arrays replaced). H2 printers pack temperatures as `target<<16 | current` in `device.extruder.info[].temp`, `device.bed.info.temp` and `device.ctc.info.temp`; older models use `nozzle_temper` etc. Updates go to the client at most every 2 s, and a printer with no report for 3 min shows offline. The access code is never logged or sent to the client. The widget picks the printing printer finishing soonest unless the user swiped in the last 2 min, and emits `activate` when a print it watched finishes or fails. Printers on the LAN announce themselves by SSDP on UDP 2021 (serial, model code, IP).
- **Accent color**: graphics use `ACCENT` from `src/frontend/theme.js`, never a color literal. It is read from `localStorage` (`DeskHud_accent`, `DeskHud_rainbow`) when the page loads. The Accent widget (`src/widgets/accent/`, no service) saves a new color or toggles rainbow mode and reloads the page, because most accents are drawn into Graphics in constructors. In rainbow mode `ACCENT` is a live binding that `index.js` switches before building each widget, so a component that uses the accent after its constructor (in `render`, a setter, or for objects created later) must copy it in the constructor (`this._accent = ACCENT`) and use the copy.
- **Demo mode**: `src/frontend/demo/DemoSocket.js` imitates the socket.io client with fake data from `*DemoData.js`. A new widget needs demo data here to show up in the demo.
- **Persistence**: services use `node-persist` (`storage.getItem/setItem`, stored in `.node-persist/`) for history data such as pomodoro history and stocks. The running pomodoro timer lives in the browser's `localStorage` (`Pomodoro_mode` is the running or next session, `Pomodoro_timerStart` is set only while one runs); only finished work sessions are sent to the service.
- **Feature switches**: `src/widgets/features.json` is read by both `widgets.js` (ES import) and `services.js` (require). `"google": false` (the default now, because the Google project is unpublished and its sign-in expires every 7 days) leaves out the Tasks widget, the Google `CalendarService` and `TodoService`, and the Calendar's Personal tab (its `messageIds` are then only `outlook`); the demo socket and the screenshot script skip them too. The code stays; set it to `true`, fill in the `google` config, rebuild and deploy to turn them back on.
- **Google widgets**: `TodoService` reads every Google Tasks list (open tasks, then tasks completed in the last `COMPLETED_DAYS`) and remembers each task's list for completing it. `CalendarService` reads the calendar IDs in `google.calendars`. `OutlookService` (`src/widgets/outlook/`, service only) reads a published ICS link (`outlook.icsUrl`) with `node-ical`, pinned to 0.25.x because newer versions need Node ≥20 and the Pi runs Node 18. Both calendar services load the 1st of this month to the end of next month. One `CalendarWidget` shows both: it lists `messageIds = ['calendar', 'outlook']`, which `WidgetContainer` routes to it (`msg2state(msg, serviceId)` gets the sender), and has Work (Outlook) and Personal (Google) tabs with per-source errors. Tapping a day on the Date & Time DATE tab emits `openDate`; `WidgetContainer` calls the calendar's `showDate` and brings it to the front.

To add a widget, follow the `create-widget` skill (`.claude/skills/create-widget/SKILL.md`). It covers registration, templates, the current visual style, config and verification.

Socket events, server→client: `config`, `widget`, `distance`, `system`, `log`. Client→server: `service` with `{serviceId, payload}`.

## Hardware notes

- No distance sensor is fitted, so `DistanceService` simulates one in-process (a timer pushing a constant 20 cm reading; it used to be a separate `distance_mock.js` process). `distance.py` is the real HC-SR04 reader and is currently unused; wiring it up means spawning it again and parsing its stdout line by line.
- HDMI power is controlled with `sudo chvt` and the `/sys/class/graphics/fb0/blank` commands in `DistanceService` (Pi 5 setup).
- Pi desktop setup (not in this repo, on `deskhud@10.168.168.159`): the labwc compositor shows the WaveShare 11.9" panel (320×1480, rotated with `transform 90` in `~/.config/kanshi/config`). Touch is mapped in `~/.config/labwc/rc.xml` by device name; labwc names USB devices with their port (e.g. `WaveShare WaveShare (USB 3-2)`), so both the plain and the port name are listed. `mapToOutput` does not apply the output's 90° rotation to touch, so the same file sets `<libinput><device category="touch"><calibrationMatrix>0 -1 1 1 0 0</calibrationMatrix>`; without it taps land at transposed positions (only the right-hand widgets visibly fail). To debug touch, compare `libinput debug-events` with where the page receives the press (`app.renderer.events.rootBoundary.hitTest`); see commit 03977e1 for a throwaway tap logger. `~/.config/labwc/autostart` waits for `http://localhost:3000` and then starts Chromium in kiosk mode with `--password-store=basic`, which avoids the keyring prompt that otherwise blocks the browser (white screen) after boot. `/boot/firmware/config.txt` uses `dtoverlay=vc4-kms-v3d,cma-256` because the 2 GB Pi ran out of graphics memory with the default.
- Pi networking and processes: the Pi has a DHCP reservation at `10.168.168.159`; `deskhud.local` (mDNS) does not resolve from the Mac on this network, so ssh and `npm run deploy` use the IP. Wi-Fi power saving is disabled on the `netplan-wlan0-PB&J` connection (it caused dropouts). pm2 watches only `src/backend` and `src/widgets` (watching `.` restarted the app whenever a service saved to `.node-persist`); a change to `watch` needs `pm2 delete desk-hud && pm2 start ecosystem.config.js --env production && pm2 save`, not a reload. `pm2-logrotate` caps logs at 10 MB × 5. The Pi 5 Active Cooler is firmware-controlled; `SysMonitorService` only reads its speed from the `pwmfan` hwmon device.
